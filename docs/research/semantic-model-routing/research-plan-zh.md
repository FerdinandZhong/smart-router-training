# 面向持续增长 Ossie 目录的低延迟语义上下文检索研究计划

日期：2026-10-10。状态：可供评审的执行方案；尚无本任务的训练或性能结果。
后续审核已形成[当前双语主计划](research-plan-bilingual.md)和[公开数据收集协议](data-collection-bilingual.md)。
数据来源、pilot 与正式样本量、评估隔离安排以双语主计划为准；本文件保留早期设计细节。
本计划采用无图检索主线，并替代早期方案中要求训练图评分器的安排。
样本量、排期、质量阈值和延迟均为规划值。

## 1. 研究问题与判断依据

研究问题：在固定延迟和 token 预算下，能否从持续增长的 Ossie 目录中检索出完整且一致的业务语义上下文？
主对照是经过调优的 keyword + embedding 检索。
主方法是语义对象索引、领域 embedding 微调和确定性依赖装配。
候选重排作为可选组件，分别比较通用重排器、GLiNER2.5-Decide 和 Laya。

“完整语义上下文”包括回答问题所需的定义、适用条件及必要依赖。
例如，“按地区统计上月净收入”需要净收入口径、地区维度和报告时间规则。
仅检索到订单表，不能证明这些信息已经齐全。
该术语描述检索输出，不是新增的 Ossie 文件格式。

| 假设 | 验证方式 | 可能的否定结果 |
| --- | --- | --- |
| H1：语义对象表示与必要依赖装配提高上下文完整性 | 对比表级文档、类型化描述和依赖装配 | 优势完全来自新增说明文字，而非表示或装配 |
| H2：领域 embedding 更能区分相近业务口径 | 对比同一骨干微调前后与调优后的 hybrid | 强 hybrid 已足够，训练未产生稳定收益 |
| H3：索引更新可以支持新表，并保持可接受的质量和延迟 | 冻结模型，更新 C1/C2 目录，再测新旧问题 | 新领域需要重新训练，或新对象造成旧问题退化 |

已有研究已覆盖 corpus-adaptive schema retrieval，以及无需在线 LLM 的多表召回与精筛。
因此，“使用 embedding”“省去图检索”或“使用 Ossie”本身不构成创新。
贡献需要落在业务定义完整性、真实增量目录和质量—延迟权衡上。
参见 [corpus-adaptive schema retrieval](https://arxiv.org/abs/2607.13311) 和 [REaR](https://aclanthology.org/2026.acl-long.1826/)。

## 2. Ossie 表示与系统边界

采用项目实际使用、能够验证的 Ossie 版本，并记录规范版本和源文件哈希。
当前官方开发稿定义数据集、字段、指标和关系。
它不等于完整的 ETL 血缘协议，也不定义通用跨模型引用。
完整血缘和跨文档标识需要明确的扩展契约。
参见 [Ossie core specification](https://github.com/apache/ossie/blob/main/core-spec/spec.md)。

第一阶段从全目录检索，但只装配同一可执行模型版本内的上下文。
跨模型候选可以构成待确认的替代解释。
未经声明的跨模型连接不进入自动执行路径。
这样可以保留万表搜索任务，同时限制首阶段的组合复杂度。

| 对象 | 检索时使用 | 装配时使用 |
| --- | --- | --- |
| 模型 | 业务域、用途、别名和适用范围 | 模型版本和准确来源 |
| 数据集 | 表的业务含义、粒度、关键字段 | 物理来源和批准的关系 |
| 指标／字段 | 口径、同义词、时间规则和排除条件 | 准确表达式、必要过滤及引用对象 |
| 血缘 | 与问题相关的来源说明 | 被请求的溯源证据；不默认拉取全部祖先 |

这些是检索系统的派生字段，不声称全部是 Ossie core 的原生字段。
派生内容必须能够回溯到已批准的定义或扩展。
缺少的业务规则保持未知，不由摘要模型补写成事实。

```text
离线：批准的 Ossie 文档 + 目录元数据
                       |
           校验、版本固定、引用解析
                       |
          +------------+-------------+
          |                          |
    紧凑语义描述                 准确定义及依赖清单
          |                          |
    关键词索引 + 向量索引           按 ID 读取

在线：问题 + 已确认历史
               |
       keyword + query embedding
               |
          候选融合与排序
               |
      可选：一次小候选集重排
               |
     定义读取、装配、预算及一致性检查
               |
       提供上下文 / 请求澄清 / 拒答
               |
          固定的 SQL 生成与验证
```

离线为指标预计算明确的计算依赖。
按查询所需维度，在线读取经过批准的定义和连接说明。
不枚举所有表组合，不运行图遍历检索或训练 GNN。
SQL 表达式只由支持该方言的解析器处理；无法解析的依赖标记为未确认。
血缘连接不能作为分析连接的替代证据。

装配器按分数加入定义及其必要依赖，并对共享定义去重。
若候选组合存在口径冲突，输出明确的澄清选项。
若必要定义超过预算，记录预算失败，不截去关键规则后继续执行。
确定性检查只能验证已声明的约束，最终语义充分性仍需人工标注和结果实验评估。

## 3. 数据准备与标注

先建立 240 个独立问题 episode 的试点。
首批 60–80 个问题用于跑通流程并测量标注工时。
通过试点后，将总量扩展至约 1,200–2,000 个独立问题。
是否足够支持结论，要结合领域数、效应大小和置信区间判断。

主数据来自真实业务问题、已审核 SQL 和经过确认的 Ossie 定义。
SQL 解析提供候选表与字段的弱标签，业务专家确认实际含义。
可以由 LLM 起草 SQL 对应问题，再交给专家审核。
这种辅助标注思路可参考 [BenchPress](https://www.vldb.org/cidrdb/papers/2026/p16-wenz.pdf)。

| 问题类型 | 必须包含的区别 |
| --- | --- |
| 直接查询 | 指标、字段或数据集的常规检索 |
| 自然表达变化 | 同义词、缩写、错别字、中英混合 |
| 相似口径 | 净额／毛额、订单／结算、事件日／入账日 |
| 多定义组合 | 指标、维度、过滤、时间与粒度的完整组合 |
| 歧义 | 两个合法解释，以及确认后的正确上下文 |
| 不可回答 | 缺失定义、缺失依赖或不支持的组合 |

自然分布问题与刻意构造的挑战集分别报告。
中英文比例来自实际使用记录，不预先设成均衡分布。
首轮可从一个真实业务域开始；跨域结论需要至少三个独立目录或领域的证据。
百表、千表和万表实验应尽量使用真实且有区分度的对象。
复制或改名生成的万表目录只能支持负载测试。

每个样本记录以下内容：问题、已确认历史、目录快照、问题组 ID、可用定义及标注来源。
监督字段包含检索锚点、完整答案依赖、合法替代集合和歧义状态。
检索锚点是问题直接寻找的指标或实体。
技术依赖可能不会出现在问题中，不强求其单独获得高检索分数。
SQL、执行结果和审核理由只作监督与评估，不能进入模型输入。

1. 冻结目录定义，再形成最终评估问题。
2. 专家标注业务意图、检索锚点和必要定义。
3. 记录所有已确认的合法替代集合。
4. 从真实检索结果中审核困难负样本。
5. 双人复核歧义与口径冲突样本，并抽查其余样本。
6. 对未解决分歧保留未知标签，并报告其数量。

按 episode、模板族和重复输入分组切分。
试点中用于修改定义或标注规范的问题，进入开发用途，不充当最终测试。
正式数据可从训练／开发／校准／测试约 60／15／10／15 的划分起步。
独立组边界优先于比例，测试规模根据试点方差调整。
最终测试标签不得用于困难负例挖掘、描述改写或 checkpoint 选择。

对新增表，冻结 C0 时训练的权重。
将 C1/C2 新表描述加入索引，但不使用未来问题训练模型或生成问题专用别名。
同时评估依赖新表的问题和原有问题的退化。
没有历史快照时，明确称为模拟到达实验。

## 4. 训练路线与模型取舍

| 顺序 | 训练对象 | 监督目标 | 继续条件 |
| --- | --- | --- | --- |
| T0 | 不训练；BM25、原始 dense、调优 hybrid | 建立召回和装配基线 | 已完成错误归因 |
| T1 | 一个可索引的双编码器 | 标准多正例对比学习，配审核后的困难负例 | 相同预算下改善完整上下文质量 |
| T2 | 通用 cross-encoder | 标准 BCE 或 pairwise ranking | 能纠正 T1 候选池内的排序错误 |
| T3 | GLiNER2.5-Decide 与 Laya | 同一问题—候选正文，masked BCE | 超过通用重排器或提供更好的质量—延迟权衡 |

主部署候选首先是 T1 加确定性装配。
T2 和 T3 在同一个冻结候选池上比较。
候选池本身漏掉的正例，不能在测试时补入。
另报 oracle 候选池诊断，避免将漏召回错误归给重排器。

embedding 的正例以审核后的检索锚点为主。
多个合法定义不能互当负例，未知候选也不能当作负例。
每轮从训练目录重新检索，再审核最容易混淆的候选。
采用标准检索目标，不增加新的成本感知损失。

先选一个适合实际语言分布的 embedding 骨干，并固定版本。
索引实验可从召回 K=20/50/100 起步。
重排实验可从 K=8/16/32 起步，并报告截断后的覆盖上限。
实际 K 由开发集的质量—延迟曲线决定。

GLiNER 和 Laya 的当前项目适配器主要训练输出模块，不能直接代表完整微调能力。
两者需要新的语义候选输入适配器。
依次比较原始 checkpoint、冻结编码器和允许编码器更新的条件。
现有路由任务的 1,300 条成功标签不能转作本任务标签。
固定源码及输入截断限制见[模型证据](model-evidence.json)和[模型训练说明](training-and-experiments-zh.md)。

1. 验证输入投影、未知标签掩码和实际 token 视图。
2. 对每种入选骨干采用相同的开发集调参次数上限。
3. 比较少量学习率配置，并记录优化步数及可训练参数。
4. 可从最多 20 epochs 起步，验证指标连续三次不改善即停止。
5. 通过开发集选择 checkpoint，通过校准集确定阈值。
6. 对入选方法运行三个随机种子，再评估锁定测试集。

epochs 和早停规则是起始设置，试点后固定。
不能因为旧实验训练十轮，就假定本任务也需要十轮。
若单 GPU 能容纳训练，优先使用单 GPU。
第二块 GPU 可运行独立候选或种子，不要求首轮引入分布式训练。
实际集群容量和可用状态应在执行阶段重新核实。

## 5. 实验矩阵

| 实验 | 固定条件 | 改变因素 | 主要输出 |
| --- | --- | --- | --- |
| E0：数据与下游上限 | 同一问题和 SQL 生成器 | 专家完整上下文／检索上下文 | 缺失语义、检索错误和生成错误的占比 |
| E1：强检索基线 | 同一可用目录和元数据 | BM25／dense／调优 hybrid／hybrid+通用重排 | 召回覆盖与完整上下文质量 |
| E2：表示与装配 | 同一来源信息和检索器 | 表级完整描述／类型化对象；无补齐／声明依赖补齐 | 语义表示和装配的独立收益 |
| E3：学习收益 | 同一表示、装配和 token 预算 | 原始／微调 embedding；各类重排器 | 收益来源及数据学习曲线 |
| E4：预算与延迟 | 同一硬件、问题集和生成器 | 2K/4K/8K 上下文；候选数量；重排开关 | 完整性—延迟曲线与系统吞吐 |
| E5：新增目录 | 冻结权重和校准策略 | C0/C1/C2；新表／旧问题；目录规模 | 新表准确率、旧问题退化、更新成本 |

表级基线必须能够访问相同的语义信息。
仅让新方法看到业务定义，会混淆数据收益和模型收益。
所有可比系统采用同一批准版本、可见范围及下游生成器。
物理 schema-only 条件可作为诊断，不能充当唯一主基线。

增加一个 REaR 风格的检索—精筛对照，以覆盖相关多表检索思路。
若将其关系发现替换为声明依赖读取，必须标明是改编实现。
保留论文原方法与我们运行条件的差异清单。
JoinGR 等图方法保留为相关工作；本阶段不要求实现或训练图方法。
因此，结论限定于所比较的方法，不能宣称超过全部图检索系统。

避免运行全部因素的笛卡尔积。
先筛选 embedding，再对最佳两种召回配置进行重排比较。
最终仅保留最有希望的两至三条流水线，完成多种子和端到端实验。

## 6. 指标、延迟与通过条件

主指标是完整上下文成功率。
对可回答且意图明确的问题，输出必须包含至少一个审核通过的完整集合。
输出还必须满足预算，并且不引入相互矛盾的定义。
允许额外的兼容上下文，但将其计入 token 和精度指标。
对本可回答的问题拒答，也计为主指标失败。

| 指标 | 计算与报告要求 |
| --- | --- |
| 候选完整覆盖率 | 候选及其可解析依赖能覆盖至少一个合法完整集合的问题比例 |
| 完整上下文成功率 | 完整、兼容且满足预算的输出数／可回答的明确问题数 |
| 冲突率 | 包含互斥口径、错误时间规则或不兼容版本的输出比例 |
| 澄清与拒答 | 在歧义、不可回答与明确问题上分别报告；同时报告覆盖率 |
| 下游业务正确率 | 固定生成器，核对业务含义和独立参考结果；执行成功率另列 |
| 时延与容量 | p50/p95/p99、吞吐、超时率、token 数和线上模型调用数 |
| 更新成本 | 新表索引时间、可检索延迟、受影响依赖更新、存储与旧问题回归 |

候选对不是独立统计单位。
按问题组进行配对 bootstrap，并报告领域宏平均及置信区间。
少数领域和稀有歧义样本的结论需要单列限制。
预算导致的不可装配问题也要报告，不能从结果中静默删除。

初始工程目标为：上下文准备 p95 不超过 500 ms。
主测试建议采用预热进程、常驻索引、关闭最终查询结果缓存的条件。
先以 5 QPS 为暂定服务负载，再测 1/5/10 QPS 的压力曲线。
这些是规划条件，第一周应根据业务需求调整并锁定。

上下文准备时间从检索服务收到请求开始，到完整上下文返回为止。
它包含排队、问题编码、索引查询、重排、定义读取和装配。
单次请求通过 trace 直接计量，不把各组件 p95 相加。
批量等待也计入在线时间。
冷启动、结果缓存命中和并发更新单独报告。

整体响应时间从应用收到问题，到最终业务回答可用为止。
它还包含 SQL 生成、数据库执行和结果解释。
该时间不能用 500 ms 的检索目标代替。
第一周测量现有整体响应时间，再分配各阶段预算。
澄清交互单列模型处理时间与用户等待时间。

快路径不增加在线 LLM 关键词提取、相关性确认或摘要生成。
最终上下文使用准确片段与固定模板。
缓存键包含目录版本和调用者可见范围；新增定义只更新受影响对象。
索引服务与定义存储尽量同地部署，减少逐候选远程读取。

正式测试前锁定实际有意义的提升阈值。
可暂用“完整上下文成功率提高 5 个百分点，且满足同一延迟预算”作为研究筛选目标。
另一目标是“质量差异不超过预定 1 个百分点边界，同时 p95 降低至少 20%”。
上述数值需由试点误差与业务要求修订，并通过置信区间评估。
点估计相近不能直接声称等效；样本不足时报告结果不确定。

## 7. 排期、资源与阶段决策

建议按 8–10 周安排，首个两周交付最小可评估版本。
排期从目录导出可用、人员落实后开始。
假设配置一名研究工程师、一名兼职集成工程师，以及两名业务审核者。
两名审核者每人每周约投入 10–12 小时。
若实际审核工时不足，优先延长数据阶段，不降低测试质量。

| 时间 | 工作 | 可审查产物与阶段决策 |
| --- | --- | --- |
| 第 1 周 | 固定 Ossie 版本，抽查语义质量，定义标注与延迟口径 | 目录清单、标注规范、整体响应基线；确定首个业务域 |
| 第 2 周 | 完成首批 60–80 问题，搭建 hybrid 和确定性装配 | 首版 E0/E1 报告；缺失定义多时先修数据 |
| 第 3 周 | 完成 240 问题试点，审核失败，固定正式实验协议 | 试点报告、标注工时、切分规则、训练继续／停止决定 |
| 第 4–5 周 | 扩充训练及独立评估问题，完成 embedding 微调 | T1 学习曲线、难例类别、召回覆盖变化 |
| 第 6 周 | 比较通用重排器、GLiNER 和 Laya | 同候选池的质量与延迟报告；决定线上是否保留重排 |
| 第 7–8 周 | 新表、规模、并发和端到端实验 | C0/C1/C2 报告、质量—延迟曲线、已知失败边界 |
| 第 9–10 周 | 补充必要样本，完成多种子验证和集成原型 | 锁定测试结果、可复现实验包、论文方法与结果草稿 |

第 4 周以后，数据审核和模型实验并行。
试点按每题 10–15 分钟主审估算，240 题需要约 40–60 人时。
第二审核者复核及争议处理需要额外时间。
正式扩充按首批实际吞吐重新估算，不假定 LLM 草稿无需人工审核。
GPU、标注和下游 LLM 的费用分别记账，现阶段不承诺未经测量的金额。

| 观察结果 | 后续决策 |
| --- | --- |
| 专家完整上下文仍频繁产生错误 SQL | 先处理定义、生成器或参考答案；暂停归因于检索模型 |
| 主要错误来自目录缺少业务定义 | 修订语义层，重新冻结版本，再开始训练 |
| hybrid 已达到要求，训练无稳定增益 | 保留工程方案，将研究结果定位为基准或系统分析 |
| 重排提升质量，但无法满足延迟目标 | 优先增加 embedding 训练或进行可选蒸馏；不强制上线重排 |
| 缺少真实多域或万表目录 | 缩小论文结论；合成规模实验只用于容量分析 |
| 新表索引后质量下降 | 分析新定义和混淆项，另报允许再训练的适配条件 |

蒸馏是后续备选，不进入首轮必做实验。
没有稳定教师收益时，不先构建蒸馏流水线。

## 8. 交付与贡献边界

第一阶段交付版本化目录、标注规范、240 问题试点和强基线结果。
研究阶段交付审核数据、训练配置、完整性评价器和延迟测试脚本。
最终交付新增表评估、模型比较、失败分析和面向 Helios/UOB 的检索接口原型。
外部数据发布范围另行确定；可先提供不含业务敏感内容的协议、代码和示例。

潜在论文贡献包含：业务语义完整性的可复现评价协议、无图检索方法，以及新增目录条件下的质量—延迟证据。
方法贡献以超过强基线的实测结果为前提。
若方法增益不足，真实基准和错误分析仍可形成独立成果，但不保证论文接收。

当前建议执行的第一步，是导出首个业务域的 Ossie 定义并审核 60–80 个问题。
该产物将同时回答数据是否可用、hybrid 的主要失败是什么，以及后续训练是否值得投入。

本计划保存在 `research/semantic-model-routing`。
原路由任务的实现、数据和实验状态由原工作目录继续管理。
